Common JSON errors and how to fix them

JSON parsers do not forgive anything. The good news is that the same handful of mistakes account for nearly every failure.

Reading the error message

A parser reports the position where it gave up, which is not always where the mistake is. "Unexpected token } at line 12" usually means something was wrong just before that brace, and "Unexpected end of input" means a bracket or quote opened earlier was never closed. Start at the reported position and look backwards. In Data Ekam, choose Format and then JSON: if the text is invalid, the message gives the line and position and the line is highlighted in the input box.

1. Trailing commas

{ "name": "Alice", "age": 30, }

JavaScript allows a comma after the last item; JSON does not. This is the most common error in hand-edited files, usually created by deleting the last line of a list. Remove the comma before the closing } or ].

2. Single quotes

{ 'name': 'Alice' }

JSON strings and keys must use double quotes. Single quotes typically arrive when a Python dictionary has been printed and pasted, because that is how Python displays one. Replace them with double quotes, and in Python use json.dumps() to produce real JSON instead of copying the printed form.

3. Unquoted keys

{ name: "Alice" }

This is a valid JavaScript object literal but not JSON. Every key needs double quotes: { "name": "Alice" }.

4. Comments

{
  // retry settings
  "retries": 3
}

JSON has no comment syntax. Some tools accept comments in their own configuration files, which leads people to believe JSON permits them, but a standard parser will reject the file. Remove the comments, or move the explanation into a key such as "_note" if the consuming program ignores unknown keys.

5. Missing commas and brackets

{
  "name": "Alice"
  "age": 30
}

Here the error is reported on the second line, although the missing comma belongs at the end of the first. Unbalanced brackets behave similarly: the parser reaches the end of the text still waiting for a ] or }. Formatting the document with indentation, once it parses up to that point, makes the unbalanced level easy to spot.

6. Values JSON does not have

JSON has exactly three literal words: true, false and null, all lower case. The following are all invalid:

  • True, False and None, which come from Python.
  • undefined and NaN, which come from JavaScript.
  • Infinity, and numbers written like .5, 5., +1 or 007. A number needs a digit before and after the decimal point and cannot have leading zeros.

7. Unescaped characters inside strings

{ "path": "C:\new\table.txt", "quote": "She said "yes"" }

Inside a JSON string, a backslash starts an escape sequence and a double quote ends the string. Windows paths need doubled backslashes, "C:\\new\\table.txt", and inner quotes need a backslash, "She said \"yes\"". A real line break inside a string is also invalid; write it as \n.

8. Invisible characters

When JSON looks perfect and still fails at position 0 or at an innocent-looking quote, suspect characters you cannot see:

  • Curly quotes. Word processors, chat apps and some email clients replace " with typographic quotes, which JSON does not recognise.
  • A byte-order mark at the very start of a file saved by some Windows editors.
  • Non-breaking spaces copied from a web page in place of ordinary spaces.

Retyping the quotes on the reported line, or pasting the text through a plain-text editor, usually clears these.

When the JSON is valid but still "wrong"

Two situations produce no syntax error and still cause trouble. The first is duplicate keys: { "id": 1, "id": 2 } is accepted by most parsers, which silently keep the last value. The second is several JSON objects one after another with no enclosing array, a format often called JSON Lines. Each line is valid on its own, but the file as a whole is not a single JSON document. Wrap the objects in [ ] with commas between them, or process the file one line at a time.

Preventing the errors

Most of these mistakes come from writing JSON by hand or by joining strings together. Let a serialiser produce it wherever you can, since a library will never forget a comma or an escape. When you do edit by hand, format the file after each change so that a mistake shows up while you still remember what you touched.
