YAML indentation errors and other common mistakes

YAML fails in two ways: loudly, with a parse error, and quietly, by loading something other than what you wrote.

How YAML reads indentation

YAML uses leading spaces to show which keys belong to which parent. There is no required number of spaces, but all the children of one parent must be indented by the same amount, and that amount must be greater than the parent's.

server:
  host: example.com
  ports:
    - 80
    - 443

Two spaces per level is the most common convention. Whatever you choose, use it everywhere in the file.

Tabs are not allowed

YAML forbids tab characters for indentation. A file that mixes tabs and spaces can look perfectly aligned in an editor and still fail with a message such as "found character that cannot start any token". Set your editor to insert spaces when you press Tab in YAML files, and turn on visible whitespace when a file refuses to parse for no apparent reason.

One space out

database:
  host: db.internal
   port: 5432

Here port is indented three spaces while its sibling has two. Depending on the parser, this is either an error or, worse, an attempt to read port as a continuation of the line above. Errors of this kind are usually reported on the line after the real mistake, so check the lines around the one named in the message.

Lists and the dash

A dash followed by a space starts a list item. When the item is a mapping, the keys after the first must line up with the first key, not with the dash.

users:
  - name: Alice
    role: admin
  - name: Ravi
    role: viewer

If role is moved two spaces to the left, it stops being part of the list item and the document either fails or changes meaning. Forgetting the space after the dash is another classic: -name: Alice is not a list item at all, just a key that begins with a dash.

Values that change type by themselves

YAML decides the type of an unquoted value by its appearance. Under YAML 1.1, which many widely used parsers still follow, that produces some well-known surprises:

country: NOboolean falsecountry: "NO"

None of these raises an error; the file loads and the wrong value travels downstream. The safe habit is to quote any string that looks like a number, a date, a time or a yes/no word.

Colons, hashes and other special characters

A colon followed by a space separates a key from a value, and a hash preceded by a space starts a comment. Both cause trouble inside unquoted text:

title: Release notes: version 2
note: use channel #general

The first line is an error because of the second colon; the second silently loses everything from #general onwards. Values that begin with *, &, !, @, %, { or [ are also treated as syntax. Quoting the value fixes all of these: title: "Release notes: version 2".

Multi-line text

For text that spans lines, YAML provides two block styles. A vertical bar keeps line breaks exactly as written, which is what you want for scripts and certificates. A greater-than sign folds the lines into one paragraph, joining them with spaces.

script: |
  npm ci
  npm test

description: >
  This long sentence is written
  on two lines but loads as one.

The block's content must be indented further than its key, and that indentation is removed when the value is loaded.

Duplicate keys

If the same key appears twice in one mapping, many parsers keep the last value without complaint. In a long file this is usually a copy-and-paste mistake, and it explains the situation where editing a setting appears to have no effect: the setting you changed is overridden further down.

How to check a YAML file

Parsing the file is the only reliable test; reading it by eye is not. In Data Ekam, paste the YAML, choose Format and then YAML. A syntax problem is reported with its line and position. To catch quiet type changes, convert the document to JSON with the Convert menu and read the result: in JSON, strings are quoted and numbers and booleans are not, so a version that has become 3.1 is immediately visible.

One caution: parsers do not all follow the same version of YAML. Data Ekam's parser follows the newer YAML 1.2 rules, under which NO and yes stay as text, while many deployment tools still apply the 1.1 rules in the table above. A value that looks right in one parser can therefore load differently in another, which is one more reason to quote anything ambiguous.
