XML vs JSON: key differences and how to convert between them

JSON replaced XML for most web APIs, but XML is still everywhere in documents, feeds and enterprise systems. Sooner or later you have to move data between the two.

The same record in both

<person id="42">
  <name>Alice</name>
  <email>alice@example.com</email>
  <phone type="mobile">98765 43210</phone>
</person>
{
  "id": 42,
  "name": "Alice",
  "email": "alice@example.com",
  "phone": { "type": "mobile", "number": "98765 43210" }
}

The JSON is shorter, but notice that someone had to make decisions to write it: id became an ordinary key, and the phone number needed a key name that the XML never had. Those decisions are the whole difficulty of converting.

Different starting points

XML was designed as a markup language for documents. Its model is a tree of named elements that can carry attributes and can mix text with child elements, as in a paragraph containing a bold word. JSON was designed to carry data structures between programs. Its model is objects, arrays, strings, numbers, booleans and null, which is what most programming languages already use internally.

That is why JSON feels natural in code: parsing it gives you a ready-made structure. Parsing XML gives you a document tree that you then have to walk.

Why conversion is not always exact

Attributes

JSON has nowhere obvious to put id="42". Converters pick a convention, commonly prefixing the key with @ or _, or merging attributes in with child elements. Whichever is used, the reverse conversion has to know the same convention to put the attribute back.

One item or many

This is the problem that causes real bugs. XML shows a list by repeating an element:

<order><item>A1</item><item>B7</item></order>

A converter sees two item elements and produces an array. But an order with a single item contains one item element, and without a schema the converter cannot know that it is a list of one. It produces a plain value. Code that expects an array then fails only on single-item orders. If you consume JSON converted from XML, always handle both shapes or normalise them first.

Types

XML content is text. Whether <zip>02134</zip> should become the number 2134 or the string "02134" is a guess, and the string is the safe one.

Text mixed with elements

Content such as <p>Read the <b>warning</b> first</p> has no clean JSON form, because the order of text and elements matters. Document-style XML is generally best left as XML.

From JSON to XML

The other direction has its own rules. An XML document needs exactly one root element, so a converter has to invent one for a JSON array or a multi-key object. Array items need element names too. And JSON keys that are not legal XML names, such as keys starting with a digit or containing spaces, have to be altered.

Characters that need escaping

In XML, & and < must be written as &amp; and &lt; inside text, and quotes must be escaped inside attribute values. A raw ampersand, often inside a URL or a company name, is the most common reason an XML file fails to parse. In JSON, the characters to escape are the double quote and the backslash.

When XML is still the right choice

  • Documents. Office files, SVG images, and publishing formats are XML because they are marked-up text.
  • Established standards. SOAP services, RSS and Atom feeds, sitemaps, and many banking, healthcare and government exchange formats are defined in XML.
  • Strict contracts. When two organisations must agree precisely on a message's structure, XSD validation is well supported and well understood.

For a new API consumed by web or mobile apps, JSON is the practical default.

Converting in Data Ekam

Paste the XML or JSON on the Transform tab, open Convert and choose the other format. The conversion follows the structure of the document, so nested elements become nested objects and the reverse. Attributes are kept as keys prefixed with @, repeated elements become an array, and element text stays a string, so 02134 keeps its leading zero. Tabular input, such as CSV, is wrapped as a root element containing one row element per record. After converting XML to JSON, check any element that can repeat, for the one-or-many reason described above, and check that identifiers with leading zeros are still strings.
