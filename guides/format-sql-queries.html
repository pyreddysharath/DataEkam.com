How to format SQL queries for readability

The database does not care how a query is laid out. The next person to debug it at 2 a.m. cares a great deal.

Before and after

This query is valid and unreadable:

select c.name,count(o.id) as orders,sum(o.total) as revenue from customers c left join orders o on o.customer_id=c.id and o.status='paid' where c.country='IN' and c.created_at>='2026-01-01' group by c.name having count(o.id)>5 order by revenue desc limit 20;

This is the same query:

SELECT
    c.name,
    COUNT(o.id)  AS orders,
    SUM(o.total) AS revenue
FROM customers AS c
LEFT JOIN orders AS o
    ON  o.customer_id = c.id
    AND o.status = 'paid'
WHERE c.country = 'IN'
  AND c.created_at >= '2026-01-01'
GROUP BY c.name
HAVING COUNT(o.id) > 5
ORDER BY revenue DESC
LIMIT 20;

Nothing about its behaviour has changed. What has changed is that you can now answer questions at a glance: which tables are involved, how they are joined, and what is filtered.

Why layout matters

SQL is read far more often than it is written. Queries are reviewed, pasted into tickets, tuned for performance and modified months later by someone else. A consistent layout also makes version-control diffs meaningful: when each column and condition is on its own line, a change shows up as one changed line instead of one enormous changed line.

The rules that do most of the work

1. Start each clause on a new line

SELECT, FROM, each JOIN, WHERE, GROUP BY, HAVING, ORDER BY and LIMIT begin their own line at the left margin. The clause keywords then form a column you can scan down.

2. One selected column per line

Listing columns vertically makes it obvious what the query returns and easy to add, remove or comment out a column. Whether the comma goes at the end of the line or the start of the next is a matter of team preference; choose one.

3. Upper-case keywords, lower-case names

SQL keywords are not case-sensitive, so this is purely visual, but separating the language (SELECT, JOIN) from your own identifiers (customers, created_at) helps the eye, especially where there is no syntax colouring, such as in logs and emails.

4. Put every join condition under its join

Indent ON beneath the JOIN it belongs to, with additional conditions on their own lines beginning with AND. Always write the join type explicitly: INNER JOIN or LEFT JOIN, never a list of tables separated by commas with the join conditions hidden in WHERE.

5. One condition per line in WHERE

Begin each line with AND or OR. When the two are mixed, add parentheses and indentation, because AND is evaluated before OR and a missing bracket changes the result without causing an error:

WHERE o.status = 'paid'
  AND (
        o.channel = 'web'
     OR o.channel = 'app'
  )

Aliases

Give tables short aliases that hint at the table name, c for customers and o for orders, and avoid t1 and t2, which mean nothing. Once a query has more than one table, prefix every column with its alias so a reader never has to guess where a column comes from. Writing AS for both column and table aliases makes them easier to spot.

Subqueries and CTEs

A subquery nested three levels deep has to be read from the inside out. A common table expression lets you name each step and read from top to bottom:

WITH paid_orders AS (
    SELECT customer_id, total
    FROM orders
    WHERE status = 'paid'
)
SELECT
    c.name,
    SUM(p.total) AS revenue
FROM customers AS c
INNER JOIN paid_orders AS p
    ON p.customer_id = c.id
GROUP BY c.name;

Indent the body of each CTE and of any remaining subquery by one level, and close the bracket on its own line.

Smaller habits worth having

  • Avoid SELECT * in saved queries. Naming the columns documents what the query needs and protects it from changes to the table.
  • Lay out CASE vertically, with each WHEN on its own line and END aligned with CASE.
  • Break long IN lists across lines once they pass five or six values.
  • Comment the why. A line such as -- excludes test accounts created by QA is worth more than any amount of alignment.
  • End statements with a semicolon, so that scripts containing several statements are unambiguous.

Consistency beats any particular style

Teams argue about leading commas, indent width and whether keywords should be right-aligned. None of it matters as much as everyone doing the same thing. Pick a style, write it down in a few lines, and let a formatter apply it so nobody has to do it by hand.
