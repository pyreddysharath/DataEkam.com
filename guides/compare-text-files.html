How to compare two text files and find the differences

"What changed?" is one of the most common questions in technical work. A diff answers it in seconds, if you prepare the two sides properly.

When a comparison saves you

  • A configuration works in one environment and not in another.
  • An API response looks different after a release.
  • Two exports that should match have different totals.
  • A colleague sends back a document and says they "changed a few things".

Reading two versions side by side by eye does not work beyond a few lines. People skim, and the difference is usually a single character.

How a line-by-line comparison works

A diff tool splits both texts into lines and finds the longest sequence of lines that the two have in common, in the same order. Everything outside that common sequence is reported as a difference: a line present only on the left was removed, a line present only on the right was added, and a removed line next to an added one is shown as a changed line. Good tools then compare the two versions of a changed line character by character and highlight the exact part that differs.

The key point is that the comparison is textual. The tool knows nothing about what the text means. Two lines that differ by one trailing space are different lines.

Comparing in Data Ekam

  1. Open the Compare tab.
  2. Paste the original into Data A and the newer version into Data B, or drop a file onto each box.
  3. Press Compare. Differing lines are highlighted, with the changed part of each line marked.
  4. Use the up and down arrows to step through the changes; the counter shows where you are, for example 3 of 12.
  5. The Differences table lists every difference in one place, which is useful for a summary.

The arrow buttons beside a change copy that line from one side to the other, so you can merge selected changes without retyping them. The layout can be switched between side by side and top and bottom, which is easier on a narrow screen. Both texts stay in your browser.

Whitespace: noise or signal?

Many differences are invisible: trailing spaces, tabs versus spaces, or a different number of blank lines. Often they are noise, and they bury the real change. The two options under the Compare boxes deal with this:

  • Ignore spaces treats lines as equal when they differ only in spacing.
  • Ignore empty lines leaves blank lines out of the comparison.

Turn them on when you are comparing prose, SQL, JSON or most code. Leave them off for formats where whitespace carries meaning. In YAML and Python, indentation is structure, so a change in leading spaces can be the bug you are looking for. In a Makefile, a tab and eight spaces are not interchangeable.

Format both sides first

This is the most useful habit in this guide. Structured data can be laid out in many ways without changing its meaning. If one JSON response is minified onto a single line and the other is indented, a line-by-line comparison reports that everything changed.

The fix is to bring both sides to the same layout before comparing. On the Transform tab, format each version with the same format selected, then paste the two formatted results into Data A and Data B. The comparison then shows only real differences. The same applies to XML, SQL and CSV.

One thing formatting does not fix is ordering. If two JSON objects contain the same keys in a different order, they mean the same thing to a program but still differ as text. When you see a block reported as removed in one place and added in another, check whether it has simply moved.

Line endings

Windows ends lines with two characters, a carriage return and a line feed, while Linux and macOS use a line feed alone. A file that has passed through a different operating system, or through some email and version-control settings, can differ on every line without a single visible change. If a comparison marks the entire file as changed and the lines look identical, line endings are the likely cause. Pasting text into a browser text box normalises line endings, which is one reason a pasted comparison can show fewer differences than a command-line diff of the same two files.

Reading the result

  • Look at the count first. Three differences and three hundred call for different approaches. A very large number usually means a formatting or line-ending mismatch, not three hundred real edits.
  • Find the first difference. In configuration and data files, one early change, such as an extra line, can push everything after it out of alignment.
  • Check both directions. Something missing from B is as important as something added to it.
  • Be suspicious of "identical". If you turned on the ignore options, remember what you told the tool to overlook.

What a text comparison cannot tell you

A diff shows that text changed. It does not show whether the change matters. 1.0 and 1.00 are different text and the same number. "true" and true look almost alike and mean different things in JSON. Use the comparison to find where to look, and your knowledge of the format to decide what the difference means.
