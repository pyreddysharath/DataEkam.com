JSON vs YAML vs TOML: which one should you use?

All three describe the same kind of data. They differ in who they are comfortable for: machines, people editing by hand, or people editing small config files.

The same data, three ways

JSON, YAML and TOML all represent the same basic building blocks: key-value mappings, lists, strings, numbers and booleans. Here is one small configuration in each.

{
  "name": "orders-api",
  "port": 8080,
  "debug": false,
  "database": { "host": "db.internal", "pool": 10 },
  "allowed_origins": ["https://example.com", "https://admin.example.com"]
}
name: orders-api
port: 8080
debug: false
database:
  host: db.internal
  pool: 10
allowed_origins:
  - https://example.com
  - https://admin.example.com
name = "orders-api"
port = 8080
debug = false
allowed_origins = ["https://example.com", "https://admin.example.com"]

[database]
host = "db.internal"
pool = 10

JSON: strict, universal, unfriendly to edit

JSON has a tiny grammar, and that is its strength. Every language has a fast, reliable JSON parser, and two parsers will almost never disagree about what a document means. This makes it the default for APIs, logs and anything one program writes for another program to read.

The cost is paid by humans. JSON has no comments, so you cannot explain why a value is set the way it is. Every key needs double quotes, a trailing comma after the last item is an error, and a deeply nested document ends in a stack of closing brackets that is easy to miscount.

YAML: readable, powerful, full of surprises

YAML removes most of the punctuation and uses indentation to show structure. It allows comments, multi-line strings, and anchors that let you reuse a block in several places. This is why Kubernetes manifests, CI pipelines and Ansible playbooks are written in it.

The flexibility has sharp edges. Indentation is significant, and tabs are not allowed for it. Unquoted values are interpreted by type, so under the older and still widely used YAML 1.1 rules the country code NO becomes the boolean false, and a version like 3.10 becomes the number 3.1. Quoting such values avoids the problem, but you have to know to do it. A long YAML file is also hard to navigate, because the meaning of a line depends on how far it is indented relative to something that may be a screen above.

TOML: obvious for small configs, awkward when deep

TOML looks like an INI file with a proper specification. Keys and values are written as key = value, sections are introduced with [table] headers, strings are always quoted, and comments are allowed. Because strings must be quoted, there is no guessing about types: "NO" is a string and 3.10 without quotes is a number, visibly. TOML also has native date and time values, which JSON lacks.

It is used for pyproject.toml in Python and Cargo.toml in Rust. Its weakness is nesting. A list of objects inside another list of objects needs repeated [[double.bracket]] headers, and beyond two or three levels the file becomes harder to follow than the YAML or JSON equivalent.

A simple rule for choosing

  • If a program writes it and a program reads it, use JSON.
  • If people edit it and the tool you are configuring already expects it, use whatever that tool expects. Kubernetes means YAML; a Rust project means TOML.
  • If people edit it, the choice is yours and the structure is mostly flat, use TOML.
  • If people edit it and the structure is deeply nested or repetitive, use YAML, and quote any string that could be mistaken for a number or boolean.

Converting between them

Because the three formats share a data model, conversion between them is usually lossless for the data itself. Two things do not survive. Comments are dropped when converting to JSON, because JSON has nowhere to put them. And key order or formatting choices, such as inline versus block lists, are decided by the converter and not carried over from the source.
